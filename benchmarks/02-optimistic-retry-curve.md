# 1.14 — 낙관적 락 재시도 횟수별 성능 곡선

로드맵 1.14. `inventory.lock-strategy=OPTIMISTIC` 고정, `inventory.optimistic-lock.max-retries`만
1/3/5/10으로 바꿔가며 경합률에 따른 성능을 비교한다.

## 측정 환경

| 항목 | 값 |
|---|---|
| Hikari `maximum-pool-size` | ← `application-dev.yml` 값 기록 |
| 대상 | inventory-service (8083), `POST /api/inventory/{id}/reserve` (3.12 신설 — 동기 전용 벤치마크 엔드포인트) |
| VUs / Duration | 50 / 30s |
| 초기 재고 | 100000 (재고 소진 자체가 목적이 아니라 넉넉하게 — 3.12, CodeRabbit 리뷰 PR #97) |
| 반복 | 워밍업 1회 + 측정 3회, 중앙값 |

## 실행 방법

```bash
docker compose -f docker-compose.yml up -d
set -a && source ./.env && set +a
./scripts/benchmark-optimistic-retries.sh
```

## 결과

로컬(Windows, Docker Desktop)에서 `scripts/benchmark-optimistic-retries.sh` 실행. 워밍업 1회 +
측정 3회의 중앙값. `실패율(5xx)`은 `server_error_rate.rate`(재시도 소진 시 던지는 503 —
`InventoryLockTimeoutException`), TPS/p50/p95/p99는 k6의 `http_reqs`/`http_req_duration`
(필터링 없는 전체 요청 기준 — 재시도를 다 소진하고 503을 반환하기까지 걸린 시간도 "체감 지연"의
일부이므로 포함).

| max-retries | TPS | p50 (ms) | p95 (ms) | p99 (ms) | 실패율(5xx) |
|---|---|---|---|---|---|
| 1 | 65.72/s | 610.81 | 1,800 | 2,610 | 84.54% |
| 3 | 53.47/s | 931.17 | 1,510 | 1,790 | 72.62% |
| 5 | 23.65/s | 1,960 | 4,290 | 6,180 | 52.36% |
| 10 | 8.76/s | 4,130 | 14,350 | 16,920 | 37.88% |

(원본: `benchmarks/raw/optimistic-retries-{1,3,5,10}-run{1,2,3}.json`, 2026-09-26 로컬 측정)

## 관찰 메모 (실측)

- **예상한 패턴이 그대로, 훨씬 극적으로 나타났다.** 재시도를 1→10으로 늘리면 실패율은
  84.54% → 37.88%로 절반 이하로 줄지만, p95는 1.8s → 14.35s로 **약 8배**, p99는
  2.61s → 16.92s로 **약 6.5배** 늘어난다. TPS도 65.72/s → 8.76/s로 **7배 이상 감소**한다 —
  VUs=50이 같은 재고 행(product_id=1) 하나를 동시에 두드리는 환경에서 재시도 자체가
  경합을 더 심하게 만드는 악순환(재시도 중인 스레드가 늘수록 다음 커밋 시도도 충돌할
  확률이 올라간다)으로 보인다.
- **"역전점"은 실패율이 아니라 체감 지연에서 먼저 온다.** 실패율은 10회에서도 계속
  줄어드는 추세라(경합이 완전히 해소되진 않았다는 뜻) 재시도를 더 늘리면 이론상 더
  떨어뜨릴 여지가 있어 보이지만, p95가 이미 14초를 넘는 시점에서는 "실패율 개선"이
  실질적 의미를 잃는다 — 사용자가 14초를 기다렸는데 그마저도 5xx를 받을 확률이
  37.88%라면, 애초에 재시도 횟수를 늘리는 것보다 DISTRIBUTED나 PESSIMISTIC 전략으로
  바꾸는 편이 나을 수 있다(01-lock-strategies.md와 비교).
- **1→3회 구간은 예상과 다르게 p95가 오히려 살짝 낮아졌다(1.8s→1.51s)**, 반면 p50은
  610ms→931ms로 늘었다. 재시도 1회 설정에서 애초에 재시도 없이 바로 실패하는 요청이
  많아 p50 자체는 낮지만, 그 소수의 "운 좋게 1회 안에 성공한" 요청과 실패 사이의
  분산이 커서 p95 쪽에 노이즈가 낀 것으로 추정된다 — 3회 반복 표준편차가 이 구간에서
  가장 컸다(원본 run1~3의 p95: 1.35s/1.48s/1.35s 대 1.48s/1.51s/2.9s).
