# 3.12 — 캐시 유무 성능 비교

로드맵 3.12. `ProductService`(1.15)의 Look-aside 캐싱을 켠 경우/끈 경우를 같은 애플리케이션에서
동시에 비교한다.

## 측정 환경

| 항목 | 값 |
|---|---|
| 대상 | inventory-service (8083), `GET /api/products/{id}`(캐시) vs `GET /api/products/{id}/uncached`(무캐시, 3.12 신규) |
| 캐시 TTL (`cache.products.ttl-ms`) | ← `application.yml` 값 기록 (기본 60000ms) |
| VUs / Duration | 50 / 30s (`scripts/benchmark-cache.sh` 기본값) |
| 반복 횟수 | 워밍업 1회 + 측정 3회, 중앙값 사용 (CLAUDE.md 측정 규칙) |
| 실행 위치 | 로컬 Docker (CI 러너 아님 — 부록 C) |

## 실행 방법

```bash
docker compose -f docker-compose.yml up -d
./gradlew inventory-service:bootRun &
./scripts/benchmark-cache.sh
```

## 결과

로컬(Windows, Docker Desktop)에서 `scripts/benchmark-cache.sh`를 **독립된 두 세션**에서
각각 실행(워밍업 1회 + 측정 3회의 중앙값). 같은 스크립트/같은 설정을 두 번 돌려 절대값의
재현성을 직접 확인했다.

| 세션 | 모드 | TPS | p50 (ms) | p95 (ms) | p99 (ms) | 에러율 |
|---|---|---|---|---|---|---|
| 1회차 | 캐시 없음 | 375.31/s | 114.44 | 204.86 | 296.29 | 0.00% |
| 1회차 | 캐시 있음 | 455.84/s | 55.73 | 201.46 | **564.86** | 0.00% |
| 2회차 | 캐시 없음 | 262.74/s | 156.90 | 311.78 | 586.30 | 0.00% |
| 2회차 | 캐시 있음 | 611.74/s | 50.92 | 167.30 | **435.66** | 0.00% |

(원본: `benchmarks/raw/cache-{uncached,cached}-run{1,2,3}.json`, 2026-09-26 로컬 측정, 재측정
전 raw 파일은 덮어써졌으므로 위 표가 유일한 기록이다)

## 관찰 메모 (실측 — 두 세션 비교)

- **TPS와 p50은 두 세션 모두 같은 방향이다.** 캐시 있음 쪽이 TPS는 항상 더 높고(1회차
  +21%, 2회차 +133%), p50은 항상 절반 이하다(1회차 55.73ms vs 114.44ms, 2회차 50.92ms vs
  156.90ms) — 절대값은 세션마다 크게 흔들려도(2회차가 전반적으로 더 느림) **방향성은
  안정적으로 재현된다.** 이 둘은 신뢰할 수 있는 결론이다.
- **p95/p99는 두 세션이 정반대 방향을 가리켰다.** 1회차는 캐시 있음의 p99가 더 나빴다
  (564.86ms vs 296.29ms, 캐시가 약 1.9배 나쁨). 그런데 2회차는 **캐시 있음의 p99가 오히려
  더 좋다**(435.66ms vs 586.30ms, 이번엔 무캐시가 약 1.3배 나쁨) — 같은 코드, 같은 설정으로
  방향 자체가 뒤집혔다. 이건 "Redisson 커넥션 풀 대기"처럼 캐시 메커니즘에 내재한 재현 가능한
  트레이드오프가 아니라, **이 로컬 측정 환경(인텔리제이 5개 서비스 + Docker Desktop/WSL2
  동시 실행)의 순간적 부하 스파이크가 p95/p99 같은 꼬리 지표를 지배하고 있다는 직접적인
  증거**다 — 2회차 자체도 cached 3회차 하나만 p95=706ms/p99=1.59s로 튀고 나머지 두 회차는
  132~167ms대였다(TPS도 그 회차만 229/s로 다른 두 회차의 1/3 수준). 부록 C가 경고하는
  "CI 러너에서 절대값을 측정하지 말 것"과 같은 이유로, 이 로컬 환경에서도 p95/p99 절대값은
  신뢰 구간이 넓다고 봐야 한다.
- **`sync=true`의 스탬피드 방지 비용은 이번 측정에서 드러나지 않았다.** TTL(60s)이 각 측정
  구간(30s)보다 길어 워밍업 이후 캐시 미스가 사실상 없었으므로, "TTL 만료 순간 첫 스레드가
  나머지를 블로킹"하는 비용은 이 벤치마크가 애초에 관측할 수 있는 구간이 아니다 — 그건
  1.17의 `ProductCacheStampedeTest`가 별도로 다루는 시나리오다.
- **결론**: 이 프로젝트의 상품 조회 캐싱은 **처리량과 중앙값 응답 시간을 확실히 개선한다**
  (재현됨). 반면 **p95/p99 같은 꼬리 지연에 대한 영향은 이 벤치마크로는 결론 내릴 수 없다**
  — 방향이 세션마다 뒤집힐 만큼 로컬 환경 노이즈에 지배당했다. 꼬리 지연 트레이드오프를
  진짜로 알고 싶다면 CI/전용 환경처럼 배경 부하가 없는 곳에서 더 많은 회차로 재측정하거나,
  Redisson 풀 사용량 메트릭을 직접 확인해야 한다.
