# ADR-0011: 재고(inventory)는 캐싱하지 않고 상품 카탈로그(product)만 캐싱한다

- 상태: 채택
- 날짜: 2026-09-20
- 관련 태스크: 1.15, 1.16

## 맥락

1.15에서 "상품 조회"에 Look-aside 캐싱을 붙이면서, `products`(이름/가격/통화)와
`inventory`(available/reserved)를 같은 API 응답에 실을지, 같이 캐싱할지를 정해야 했다.
로드맵 1.16은 "재고 변경 시 캐시를 어떻게 무효화할지"를 묻지만, 먼저 "애초에 캐싱해도
되는 값인가"부터 판단해야 무효화 전략을 설계하는 의미가 있다.

## 검토한 선택지

### A. 상품+재고를 하나의 응답으로 묶어서 캐싱하고, 재고 변경 시 `@CacheEvict`로 무효화
- 장점: 클라이언트가 한 번의 호출로 가격+재고를 모두 얻음
- 단점: 재고는 주문마다(1.11의 모든 락 전략에서) 바뀐다. 캐시 TTL 안에서도 실시간성이
  필요한 값이라 사실상 매 쓰기마다 무효화해야 하고, 그러면 캐시 히트율이 의미 없는 수준으로
  떨어진다. 동시성 테스트(1.12, 재고 100·동시 300건)처럼 초당 수백 건이 갱신되는 값을
  캐싱하면 무효화 신호 자체가 병목이 된다.

### B. 상품(이름/가격)만 캐싱하고, 재고는 항상 DB에서 직접 읽는다 (채택)
- 장점: 캐싱 대상이 실제로 "자주 안 바뀌는" 데이터로 좁혀져 무효화 로직이 필요 없어진다.
  재고 조회는 1.11의 락 전략(특히 PESSIMISTIC/DISTRIBUTED)이 이미 DB 행 자체를 락으로
  보호하므로, 캐시가 끼어들면 오히려 "락은 최신 값을 잠갔는데 캐시는 stale한 값을 보여주는"
  불일치가 생긴다.
- 단점: 상품 조회 API를 호출할 때마다 재고는 별도로 DB를 때려야 한다(캐시 이득 없음).

## 결정

**B를 채택한다.** `ProductService`(1.15)는 `Product`(이름/가격/통화)만 `@Cacheable`로
캐싱하고, `InventoryService`/`InventoryRepository`에는 캐시를 전혀 붙이지 않는다.
`GlobalExceptionHandler`나 API 응답 설계에서도 재고 수량이 캐시를 거치는 경로를 만들지 않는다.

## 근거

CLAUDE.md 코드 규칙: "재시도를 붙이기 전에 그 호출이 멱등한지 먼저 확인" 같은 원칙과
마찬가지로, "캐싱을 붙이기 전에 그 값이 얼마나 자주 바뀌는지 먼저 확인"해야 한다.
재고는 이 프로젝트에서 1.11~1.14의 동시성 실험 대상 그 자체이고, 정합성이 최우선인 값이다.
반면 상품 이름/가격은 운영자가 수동으로 바꾸는 정도의 빈도라 TTL 기반 캐싱과 눈에 띄는
staleness 허용이 합리적이다.

## 결과

- 이 결정으로 생긴 제약: 상품 상세 API에 재고 수량을 함께 노출하려면(현재는 노출 안 함)
  재고 부분만 캐시를 우회해 별도로 조회해야 한다 — 응답을 합성하는 서비스 레이어가 필요.
- 나중에 다시 볼 조건: 2단계에서 Inventory Service가 별도 프로세스로 분리되면, 상품
  조회(Order/Payment 쪽)가 Inventory Service를 매번 동기 호출하는 대신 "예약 가능 여부"
  정도의 훨씬 약한 신호를 짧은 TTL로 캐싱하는 게 나을 수 있다 — 그때는 재고 자체가 아니라
  "예약 가능/불가" 같은 파생 값을 캐싱하는 것이므로 이 ADR의 "재고 원값은 캐싱 안 함"
  원칙과 모순되지 않는다.
